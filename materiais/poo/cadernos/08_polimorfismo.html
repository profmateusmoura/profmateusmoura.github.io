Polimorfismo e estratégias

Trocar um comportamento mantendo a forma de uso pelo cliente.

COMO ESTUDAR

Leia as explicações em ordem, acompanhe o código e só depois abra os exemplos completos no ZIP. Não é preciso ter usado classes antes de começar esta trilha.

1. Uma pergunta, respostas implementadas de formas diferentes #

Um orçamento pode calcular frete por uma regra fixa ou oferecer retirada gratuita. Em vez de colocar todas as alternativas dentro do orçamento, podemos fornecer um objeto responsável por calcular o frete. O orçamento usa a mesma operação, sem conhecer a fórmula concreta.

Isso é uma forma de polimorfismo: objetos diferentes atendem a uma interface esperada. Em Python, eles não precisam obrigatoriamente herdar da mesma classe para esse exemplo funcionar. O importante é oferecer calcular_centavos com o contrato combinado.

2. O contrato inclui tipo e unidade #

Se uma estratégia retorna reais e outra centavos, o nome comum do método não basta para tornar a colaboração correta. Aqui todas retornam um inteiro não negativo em centavos. O orçamento soma valores compatíveis.

O exemplo usa estratégias simples para deixar a troca visível. Em um projeto maior, testes e eventualmente abstrações formais podem ajudar a documentar a interface. Não introduza uma hierarquia apenas para dar um nome sofisticado a duas funções; use a solução que deixa a responsabilidade clara.

3. Injetar a colaboração facilita testar #

Receber a estratégia no construtor permite escolher o comportamento de fora. O orçamento não precisa criar uma implementação específica nem consultar uma configuração global. Um teste pode fornecer uma estratégia de valor conhecido e conferir a soma.

Esse desenho favorece a inversão de dependências no sentido prático: o cliente depende de uma capacidade esperada, não de detalhes de uma implementação fixa. A flexibilidade vale quando há uma variação real a representar, não como exigência para todo programa pequeno.

4. Um exemplo acompanhado

O programa abaixo é completo e independente. Antes de executar, procure o estado inicial e a operação que produz o resultado. Os comentários documentam as responsabilidades.

Python
class FreteFixo:
    """Calcula um frete fixo didático em centavos."""

    def calcular_centavos(self):
        """Retorna 500 centavos."""
        return 500


class RetiradaNaLoja:
    """Atende ao mesmo contrato sem custo de frete."""

    def calcular_centavos(self):
        """Retorna zero centavos."""
        return 0


class Orcamento:
    """Recebe uma estratégia de frete em vez de escolher seu tipo."""

    def __init__(self, subtotal, frete):
        """Recebe subtotal válido em centavos e estratégia compatível."""
        self.subtotal = subtotal
        self.frete = frete

    def total(self):
        """Soma subtotal e frete na mesma unidade."""
        return self.subtotal + self.frete.calcular_centavos()

print(Orcamento(2000, FreteFixo()).total())
Saída
2500

Compare outras duas situações

Os trechos seguintes usam as mesmas definições acima. Cada um começa com novos objetos; não reutilize o estado de uma execução anterior.

print(Orcamento(2000, RetiradaNaLoja()).total())

6. O que levar deste caderno

Trocar um comportamento mantendo a forma de uso pelo cliente. Não. O cliente pode usar a operação contratada; testes de tipo para cada variante eliminariam parte dessa flexibilidade.

Ao explicar uma solução, identifique quem guarda os dados, quem pode alterá-los e quais condições precisam continuar verdadeiras. Se não conseguir justificar uma mudança, volte ao código e acompanhe a primeira instrução em que sua previsão divergiu.
